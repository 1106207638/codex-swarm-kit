# 蜂群协作运行规则

用户当前指令、宿主指令层级及目标项目的审批和安全约束优先。本包不提供额外授权。保留既有唯一项目计划，不另建竞争流程。

1. 先明确目标、范围、可观察验收。简单问答和小修由主线程直接完成。复杂任务先向用户展示模块、依赖和验收，获得实施授权后才执行；每批只做当前模块，核对产物、运行证据和独立审核后放行下一模块。只分析的请求止于分析。
2. 主线程负责方向、调度、分歧裁决、高风险判断和最终验收；有大纲协作默认要求宿主实际 gpt-6-astra，遵守明确的模型限制。普通路径不因主线程不是 Astra 而阻塞。桌面手选仅是主线程起始偏好；只有用户明确固定时才固定。只有明确“全任务同模型”才向全部子项传递 override，统一型号不自动统一强度。
3. 按任务收益委派：技术规划和未知根因调查用 sol_planner/high（明确复杂 max）；独立审核 sol_architect/max；方案明确的实现 luna_worker/medium；复杂状态、并发和兼容 luna_deep/high；整理 luna_general/medium；多来源研究 terra_general/high。角色完整职责见 runtime/agents。规划者与审核者必须独立上下文，一个问题一个执行者。同库可能并行，禁止恢复或覆盖他人修改。
4. 每次新派发以当次同一原生调用入口的工具声明为准。Sol/Luna/Terra 只从完整 gpt-数字版本-家族 稳定型号中按数字元组取最高可用版本，所需 effort 必须支持。角色 TOML 是兼容快照，不是实时目录。角色新增权限无法等价保留、型号缺失、含糊或所需 effort 不支持时停下该委派，不猜型号，不退旧版。使用 default、fork_turns=none、明确型号和 effort，完整角色限制随任务包传入；不声称 OS 只读隔离。
5. 模型/权限故障先留证并交用户选择，不静默换模。保留 Spark 原子任务可用性故障后同包转一次 Luna/medium 的唯一例外；本 CLI 不自动执行 Spark 通道。普通逻辑失败不触发该例外。非预期验证失败先报告中枢，中枢定位根因再修；连续两轮同类失败停下请用户决定，三次尝试预算跨输入版本保留，不换任务 ID 洗掉失败。
6. 使用同胶囊唯一 model-routing-state 台账。恢复先 status：未知派发不重发，不以超时证明停止；明确宿主停写后才能 reconcile。新派发 prepare→原样宿主 spawn_args→立即 bind→report→中枢核对实际结果与停写证据→verify。direct 用 complete_direct；report 不代表验收。详见 CONTRACT.md。工具声明与成功派发不等于实际后台型号证据；无宿主元数据就记 unknown。
7. 新委派用文件任务包，代理按 bootstrap 指定 shell 只读校验 SHA/attempt 并读完整角色职责。失败不猜路径、不修包、不读额外台账，立即回报。成功报告带 packet_sha256；中枢核实际读取输出和原包。已知验收预先填写 check_plan，真实退出码和原始输出先 record_check，不在失败后改预期洗绿。审核工具使用显式 read_paths/snapshot_files/artifacts，metadata 不授权读取。
8. 主线程每次派发核真实总名额，同一台账最多两名活动子代理，未知派发占名额；不得由子代理继续分裂绕上限。相同 attempt 同型号/强度可 followup；新 attempt、换模和独立审核必须新上下文，确认旧执行者停止。目录约束仅覆盖共享台账，不是 OS 锁。
9. 有实质大纲且获准实施时按 OUTLINE.md 登记目标、模块、固定任务身份、验收映射；只派当前模块，outline_accept 后进入下一批，outline_complete 核集成。不能把业务标为 controller、降低真实 risk 或省略 mode 绕过约束。高风险业务自动拆分当前不支持，保持真实风险并由中枢调整执行安排，必要时问用户。
10. 主线程切换只在有收益的交接点，不能在同一运行轮次热换。按 RUNTIME.md 核实际入口、明确消息授权、prepare/stage/confirm。默认用户新消息启动；仅用户明确创建 Goal 且另具消息许可才采用 Goal 来源。staged 只表示设置保存；新轮核实际型号才确认。未知、冲突和模型故障不重发。未提供相关原生工具则如实说明可选能力不可用，不伪造运行证据。
11. 子任务包必须包含 goal/input/path及所有权/constraints/forbidden/success/verification/escalation，完整保留全任务限制。输入冲突、范围/公共契约/架构/审批变化、不可逆或隐私风险立即停止扩大操作并回报中枢。
12. 每批回到原验收记录成果、证据、剩余差距和下一步。连续两个有效检查点无可用成果/新证据时先复判路线，不扩支线。完成前逐项覆盖对账；代码审核不能替代运行态验收。必要项失败或未验保持开放。无公平实测不宣称速度、成本收益；应用退出后不承诺后台运行。
13. 通过调度入口操作现有台账时自动留下调用日志。排查时用 `call_log` 按任务、尝试或单次调用编号查看，结合 `status` 与宿主回执判断下一步。日志结尾缺失时先对账。
14. 外接 local_worker 由总控按 [EXTERNAL-WORKER.md](EXTERNAL-WORKER.md) 派发。适合有材料、有标准、可核对的文字任务时，填写 external_worker 并核本次服务能力。通过 prepare、真实 MCP 提交、external_bind、external_poll 和 verify 留证。候选结果需总控验收，执行、规划和独立审查继续按其职责安排。
15. 普通协作开始时为同一用户目标下的所有工作项登记同一个新的 recap_scope，大纲协作用已登记的大纲范围。每次处置子任务结果，用 recap_note 摘要记录分工、结果、采纳/部分采纳/退回/未采用及理由。正常收尾或提前终止前，主线程沿返回的 recap_query 或按当前范围执行 swarm_recap。used 为真，最终答复写「本次任务使用了蜂群协作」，逐项交代谁做了什么、输出、总控处理及理由，并提供各项可核对的日志位置。展示影响交付的依赖、返工与版本变化。任务多时，聊天概括全部分工及失败项，随附完整可读明细。直接执行照常收尾，缺回执、缺摘要、日志损坏或缺行均如实交代。参见 [复盘调用约定](CONTRACT.md#蜂群任务复盘)。
